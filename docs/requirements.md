## 1. 背景と目的

### 1.1 企画

| 項目 | 内容 |
|---|---|
| テーマ | 未来のPRネタを作り出す |
| 内容 | 今後のイベントの詳細内容について、プレスリリースでより多くの反響を得そうな内容を基に決定する |
| 背景 | プレスリリースを継続的にやってもらいたい、ネタを作り出してあげたい |
| 対象 | 一回離れて、営業の働きかけで復帰した顧客 |

### 1.2 位置づけ

休眠からの**復帰は営業が既に達成している**。営業アウトバウンド × 事例提案という打ち手が効いており、営業本人が「割と戻ってきてもらえている」と述べている（復帰率は非開示）。

本企画が解くのは復帰ではなく **定着（2本目以降を継続してもらうこと）**。営業が挙げた未解決課題「戻ってきてからどう継続してもらうか」「1回目で終わらせない」「ネタがない」に直接対応する。

### 1.3 介入する時点が特徴

一般的なPR支援ツールはリリース原稿を書く段階に介入する。本企画は**その手前、これから実施する取り組みの中身を決める段階**に介入する。「どう書くか」ではなく「何をやるか」を、PRの届き方から逆算して決める。

## 2. 解決する課題

### 2.1 離脱理由（PR TIMES営業部ヒアリング・一次情報）

| 順位 | 理由 |
|---|---|
| 1位 | 期待値に達しなかった |
| 2位 | 何をどのように出せばいいかわからない |
| 3位 | ネタがない |

※ 3理由の再開率は「同じくらい」とも言われており、2位が「1番引き戻しやすい」という注記と矛盾している。**未解決。**

### 2.2 実測が示す構造

**1本で止まる企業が最大の壁**（実測・提供DB）

| 配信本数 | 企業数 | 構成比 |
|---|---|---|
| 1本のみ | 43,617 | 35.4% |
| 2本 | 18,014 | 14.6% |
| 3-5本 | 22,266 | 18.1% |
| 6-10本 | 13,302 | 10.8% |
| 11本以上 | 26,064 | 21.1% |
| **合計** | **123,263** | |

> **注意**: これはライフタイム本数の構成比であり、遷移確率ではない。右打ち切り（現在1本の企業が今後2本目を出す可能性、直近入会ほど本数が少ない）を含む。「1→2で64.6%が脱落」のような遷移率として読んではいけない。正しく出すには `company_id` 内の `created_at` 系列でコホートを切り、観測期間を揃えて「初回からX日以内の2本目到達率」として再計算する（提供DBだけでできる）。

**経験を積んでも1本あたりの成果は上がらない**（実測・提供DB）

| 何本目 | 件数 | 転載中央値 | 転載平均 | PV中央値 | PV平均 |
|---|---|---|---|---|---|
| 1 | 123,263 | 31 | 32.7 | 15 | 46 |
| 2 | 79,646 | 31 | 32.8 | 13 | 41 |
| 3 | 61,632 | 31 | 32.7 | 13 | 44 |
| 5 | 44,319 | 31 | 32.7 | 13 | 43 |
| 9 | 30,074 | 31 | 33.0 | 13 | 58 |

**この事実が企画の存在理由になる。** 「慣れれば上手くなる」なら外部ツールは要らない。慣れても上がらないからこそ介入に価値が出る。

ただし解釈は2通りあり、**社内で統一しておくこと**。

- 解釈A: 転載は原文自動転載の仕組み（配信後に審査し問題なければ一斉案内）なので、書き手の習熟に依存しない
- 解釈B: 内容の質が成果に効いていない

**採用するのは解釈A**。理由は §13 Q1 を参照。

## 3. 対象ユーザー

### 3.1 プライマリ

**一度離れて、営業の働きかけで復帰した顧客企業の広報担当・経営者。**

広報専任がいない企業がほとんど。本業が別にある。

### 3.2 ペルソナ（商談議事録3件・実在）

| | ①菓子＋福祉（熊本・本間様） | ②土木コンサル | ③きずなノート（KOTONOHA・深谷様） |
|---|---|---|---|
| 配信実績 | 4件 | 1件（2022年8月） | 2件＋YouTube分 |
| 停止期間 | — | 約2年 | 約1年 |
| 成果 | 問い合わせ・掲載 **ゼロ** | 51媒体転載（本人は未認知） | 40媒体・20媒体転載（本人は未認知） |
| 自己診断 | 「たぶん伝え方の問題」 | 結果自体を知らない | 「ああそうなんだで終わる」懸念 |
| ゴール | 売上（福祉事業を支える原資） | 認知拡大 | 購入（子世代への訴求） |
| ネタ | **下書き約500個あるが未発信** | 採用PR・表彰（機能確認の質問止まり） | 商品1つのみ |
| 制約 | 「忙しくしすぎると福祉事業が回らない」＝露出量に自ら上限 | 事業部に決裁権限なし | 「人数が少なくイベントをやる時間がない」 |

**設計上の含意**

- ③は**新規の催しを要求する提案は実行されない**
- ②のような「催しを伴わない組織の変化」も予定として扱う必要がある

## 4. スコープ

### 4.1 やること

- 復帰顧客が持つ「これからやろうとしていること」を1行入力させ、**対話で内容を具体化する**（壁打ち）
- 具体化する項目は、追加コストゼロ〜15分で足せるものに限る（場所・相手・当日の人・初・見聞き・既存動画）
- **聞く順序は実測の効果量で決める。** 現在は場所を最初に聞く（§5.2 U1）
- やることが思いつかない顧客には、**既にやっていることを聞き出して予定候補に変換する**（ヒアリング）

### 4.2 やらないこと

- 復帰そのもの（営業が既に達成している）
- スコアの数値を顧客に見せること
- 反響の絶対値予測
- 顧客に新しい取り組み・新しい運用体制を作らせること
- 「今回は見送りましょう」という出力
- **過去の配信結果の可視化**（媒体リストもPVも PR TIMES のコンソールに既にある）
- **原稿の書き方の支援**（テーマは「どう書くか」ではなく「何をやるか」。§1.3）

## 5. 前提と制約

### 5.1 設計制約（破ってはいけない）

| # | 制約 | 根拠 |
|---|---|---|
| 1 | スコアの数値を顧客に見せない | 離脱理由1位が「期待値に達しなかった」。数値は期待値を吊り上げる |
| 2 | 出力は必ず「出す方向」に働く。見送り提案を出さない | ①③は既に自己検閲している。低評価は先送りを機械が追認する |
| 3 | 断定的な数値予測を顧客に見せない | 外れると信頼を失う |
| 4 | 転載数・PVをそのまま成果として提示しない | 顧客のゴールは①売上・③購買。「31件載ってこれか」になる |
| 5 | 顧客側の新規努力を前提にしない | ③「人数が少なくイベントをやる時間がない」 |
| 6 | 露出量に上限を置く顧客に増産を迫らない | ①「忙しくしすぎると福祉事業が回らない」 |
| 7 | ハッカソンでは「動くもの」を作る | チーム決定 |
| 8 | Q1未確認。依存部分と非依存部分を分ける | §5.2 |

### 5.2 検証結果（2026-08-13 実測。詳細は `docs/findings.md`）

| # | 前提 | 結果 |
|---|---|---|
| **U1** | **「実施内容を変えると届き方が変わる」** | **肯定。** 同一企業 × 同一リリース種別内で、地域情報のある本と無い本を比べると **95.4% のセルで地域ありが勝つ**（ユニーク媒体数の中央値差 +17.5）。拾っているのは**みんなの経済新聞ネットワークと地方紙**。ただし動画は 49.1% で**差が無い** |
| U3 | 目的変数の分散 | **`wc_uniq` に分散あり**（p10=22 / p50=31 / p90=47 / sd=10.5）。目的変数として使える |
| U4 | like_count | **使えない。** 49.4% がゼロ |
| U5 | main_image_face | **列が存在しない。** 検証不能。チェック項目「人が写った写真」はDBで裏を取れない |
| U6 | 31 はスパイクか中央値か | **なだらかな分布の中央値。** 最頻値は 27〜28。「自動転載枠で31に固定される」という解釈は支持されない |
| U7 | 「顧客は確定予定を1件は持っている」 | 持たない顧客向けにヒアリング（既にやっていることの抽出）を用意して回避した |

**U1 が肯定されたことがこの企画の根拠**である。テーマ「より多くの反響を得そうな内容を基に決定」に対して、
「市区町村名を1つ入れると、その地域の経済新聞と地方紙が拾います」という、数値を出さずに具体的で
実測に基づく一文が言えるようになった。

#### 未検証のまま残っているもの

| # | 前提 | 影響 |
|---|---|---|
| U2 | 「1つの出来事を3回に割ると届く先が広がる」 | **3枠分解を製品から外したため、検証不要になった** |
| U8 | 「営業が復帰商談で棚卸しの時間を割ける」 | **ヒアリング機能が顧客自身で棚卸しできる形にしたので、単一障害点ではなくなった** |
| U10 | PR TIMES の課金モデルと本数増の整合 | 未確認 |

#### U1 の限界（審査で聞かれたら正直に答える）

- **相関であって因果ではない。** 「地域を書いたから広がった」のか「地域を書くようなリリースが
  そもそも広がりやすい」のかは、この設計では区別できない
- 企業・業種・リリース種別は固定したが、**同じ企業でも力を入れたリリースほど地域も書くし届きもする**
  という交絡は残る
- 拾う媒体の特定（`findings.md` §4.3）は1セル（n=110 vs 279）の結果。他業種での再現は未確認

### 5.3 中核仮説の衝突（**解消済み**）

> 旧: データは「回数を重ねても1本あたりは良くならない」と言っている。
> では顧客が2本目を出す理由は「総量が増えるから」しかない。
> ところが総量＝露出量を成果として出すことは制約4で禁じ、増産を迫ることは制約6で禁じている。

**実測で解消した。** §2.2 の表が示していたのは「**配信本数を重ねても上がらない**」であって、
「何をやっても変わらない」ではなかった。同じ企業・同じリリース種別の中でも、**実施内容の違いで
届く媒体の数は 95.4% のセルで差が出る**（§5.2 U1）。

したがって顧客が次を出す理由は「量を増やすため」ではなく、
**「同じ手間でも、中身の決め方で届く先が変わるから」**である。制約4とも制約6とも衝突しない。

### 5.4 本数は増えるのか

**増えない。** 3枠分解（1つの出来事を3回に割る）を製品から外したため、
この製品は配信本数を増やす装置ではなくなった。

増えるのは**1本あたりの届き先**である。顧客の作業量も増えない
（追加コスト0〜15分の要素しか求めない。制約5・6を守る）。

## 6. 機能要件

機能は2つだけ。どちらも RDS にも DuckDB にも接続せず、OpenAI だけを使う。

### 6.1 壁打ち（主機能）

顧客が既に持っている「これからやること」を、対話で具体化する。**顧客は原稿を書かない。イベントの中身を決める。**

- 入力は「これからやることを1行」だけ。**案を生成するボタンは無い**。これが「AIでネタ出しするツール」との唯一の可視的差分（§13 Q5）
- AI が1問ずつ聞き、返答から項目を埋める。1回の返答で複数項目が埋まることがある
- **聞く順序はサーバーが持つ固定順。フロントは順序を持たない**
- 全項目が「埋まった」か「該当なし」になったら完了

| 順 | code | 質問 | 埋まると何が起きるか | tone |
|---|---|---|---|---|
| 1 | `place` | どこでやりますか。市区町村まで | 市区町村名を1つ入れると, その地域の経済新聞と地方紙が拾います | **causal** |
| 2 | `partner` | 社外で関わる相手はいますか | 相手先の名前が入ると, 相手側の関係者にも届きます | functional |
| 3 | `people` | その日, その場に人はいますか | その場にいる人が写っていると, 何が起きたのかが伝わります | functional |
| 4 | `novelty` | 御社として初めてのことはありますか | 「初」が言い切れると, 何が新しいのかが読み手に伝わります | functional |
| 5 | `observation` | 当日見聞きしたことを1つ書き留められそうか | その場で見えたことが1つあると, 発表文が具体的になります | functional |
| 6 | `video` | すでにある動画はありますか | 動画があれば添えられます。無ければ撮らなくて構いません | functional |

**`place` を最初に聞く根拠は実測**（§5.2 U1）。同一企業・同一リリース種別内で 95.4% のセルで地域ありが勝ち、
ユニーク媒体数の中央値差は +17.5。拾っているのは地域経済新聞と地方紙。
**`video` を最後にする根拠も同じ実測**で、勝率 49.1%（差が無い）。

**`tone` の規約（自動降格）**: 判定クエリを通った項目だけ `causal`（「〜する傾向があります」と因果を書いてよい）。
通らなかった項目は `functional`（因果を主張せず機能説明に留める）。**現在 `causal` は `place` のみ。**
この降格は実装規約とし、省略を許さない。フロント側で因果表現を足すことも禁止する。

**答えられないときの扱い**

| 返答 | 挙動 |
|---|---|
| 明示的に「無い」「決まっていない」 | 該当なしとして記録し、次へ進む |
| 粒度が足りない（地名が「関東」だけ） | **`place` だけ1回聞き直す。** 効果量が突出しているため1往復であきらめない |
| 2回目も読み取れない | 打ち切って次へ進む。同じ質問を繰り返さない |

### 6.2 ヒアリング（入口）

「やることが思いつかない」顧客から、**既にやっていること**を聞き出して予定候補に変換する。

- **質問は LLM が生成する。** 直前の返答を踏まえて深掘りするか、空振りなら話題を変える
- 質問は「すでにやっていること・すでに決まっていること」だけを聞く。**新しい取り組みを促す質問をしない**
  - × 「イベントを開催してみてはいかがですか」
  - × 「SNSを始める予定はありますか」← 予定を聞く形だが、始めることを促している
- 候補が3件たまる / 6往復を超える / 3回続けて「特にない」— のいずれかで終了
- 候補を選ぶと、その内容を持って壁打ちへ渡る

**「予定」の定義**（イベントに限定しない。③対策）

日付が決まっている／決められる「変化」を全て予定として扱う。

1. 販売・提供の開始/拡大
2. 提携・連携の開始
3. 場所・チャネルの追加
4. 商品・サービスの改訂
5. **人・組織の変化**（②の事業部新設）
6. 受賞・認定
7. **数字の節目**（累計・周年）
8. 外部イベント出展

③のように人手がなく催しを開けない企業は 4・5・7 だけで運用でき、新規の催しを一切要求しない。
実測でも、③相当の顧客（「商品1つを3年作っている」だけ）から候補を抽出できることを確認済み。

### 6.3 削除した機能と理由

| 旧 | 削除理由 |
|---|---|
| F1 届き先の可視化 `/reach` | 媒体リストとPVは **PR TIMES のコンソールに既にある**。再表示しても何も足さない |
| F7 72時間メール / `/inbox` | 同上。「顧客が見に行かない」を解く価値は認めるが今回のスコープ外 |
| F3 3枠分解（前/当日/後） | テーマは「イベントの中身を決める」であり、発信計画の分解は別の問題 |
| F4 原稿ドラフト生成 | §1.3 の「どう書くかではなく何をやるか」から外れる |
| F6 素材ライブラリ | 壁打ちの入口としてヒアリングを置いたため不要になった |
| F8 露出上限の自動繰り越し | 3枠分解の廃止に伴い前提が消えた |
| `guard.py`（数値遮断第3層） | **顧客自身の事実を誤検出して黙って捨てていた。** 「去年から客足が増えました」が `増えま` に一致して落ちる。制御は プロンプトと構造化出力スキーマ（第1・2層）が担う |

## 7. 非機能要件

| 項目 | 要件 |
|---|---|
| 数値遮断 | ① **プロンプト**で禁止事項を例つきで明示（「PVが120になります」「30%向上」等の×例を書く）② **構造化出力スキーマ**の型と `Field(description=)` で書ける形を縛る。`delta` / `se` / `score` に相当するフィールドを持たせない |
| 正規表現による事後チェック | **採用しない。** 顧客自身の事実（「客足が増えました」）を誤検出して黙って捨てる害の方が大きいことを実測で確認した。自由文の原稿生成を実装する場合は、その出力にだけ効く形で再検討する |
| 実測値の表示 | **未測定の件数を画面に出さない。** 実測に裏付けのある文言だけを `causal` として出す |
| RDS | **読み取り専用。DDLも書き込みもしない。** アプリは接続しない（ETL のときだけ使う） |
| クエリ安全 | 全セッションで接続時に `SET statement_timeout` と `SET default_transaction_read_only = on` を強制する。API は 10秒、ETL はチャンクが収まる値。`webclipping_list` への剰余サンプリング（`% N`）を使わない（インデックスが効かず全走査になる） |
| 応答時間 | 壁打ちもヒアリングも毎ターン LLM を呼ぶため数秒〜十数秒かかる。フロントは `AbortSignal.timeout(30_000)` を付け、送信中は入力を落とす |
| 状態の永続化 | **サーバーに持たない。** クライアントが `draft` / `history` を持ち回る。リロードで消えないよう、フロントが `sessionStorage` に保存する |
| モデル | `gpt-4.1-mini` を主、`gpt-4o-mini` を fallback に固定。環境変数では切り替えない |
| 秘密情報 | `.env` と鍵ファイルのみ。Git・ソース・Slack・ログに貼らない。アプリは `.env` を自分で読まず、実行側（`uv run --env-file` / compose）が渡す |

**しない。** 壁打ちもヒアリングも状態をサーバーに持たず、クライアントが持ち回る。

```bash
# RDS は PubliclyAccessible: false。ローカルからは EC2 経由の SSH トンネルが要る
ssh -i <key.pem> -N \
  -L 15432:prtimes-hackathon-2026summer-db.cnum2840eavk.ap-northeast-1.rds.amazonaws.com:5432 \
  ubuntu@13.112.91.188

# ETL（DATABASE_URL はトンネルを指す）
cd backend
uv run --env-file ../.env python -m etl.extract
uv run --env-file ../.env python -m etl.load_duckdb

# API（ローカル）
uv run --env-file ../.env uvicorn app.main:app --port 8080

# フロント（別ターミナル）
cd frontend && bun install && bun run dev
```

**自宅IPが変わると EC2 に届かなくなる。** `curl -4 -s ifconfig.me` で確認し、
セキュリティグループ `sg-03555db1c40d124bf` の 22/80/8080 を張り替える（`docs/infra.md`）。
