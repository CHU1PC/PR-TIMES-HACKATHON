# プレスリリースの読まれやすさ予測 - k-NN ベースラインとの比較

## 結論

**勝った。ただし時系列分割では「有意差なし」の一歩手前。**

Spearman と、k-NN との差の 95% 区間 (paired bootstrap):

| 分割 | k-NN ベースライン | LightGBM | RandomForest |
|---|---|---|---|
| ランダム (企業単位) | 0.3586 | **0.4218** (+0.0632, [+0.0537, +0.0727] 有意) | 0.3796 (+0.0210, [+0.0110, +0.0314] 有意) |
| 時系列 (企業単位) | 0.3390 | **0.3588** (+0.0198, [-0.0006, +0.0387] **ゼロをかすめる**) | 0.3241 (**-0.0149**, [-0.0388, +0.0068]) |

**RandomForest は LightGBM に届かず、時系列分割では k-NN ベースラインすら下回りました** (詳細は 5.1)。採用は LightGBM のままです。

**Lambda には載る。** 依存 (lightgbm + numpy + scipy) と モデルで解凍後 155MB。上限 250MB に対して 95MB の余裕。

- 順位精度はどの分割・どの指標でもベースラインを上回った。ただし時系列分割の勝ち幅 (+0.02) は誤差と紙一重で、「明確に勝った」と言えるのはランダム分割だけ。
- 受け入れテストの順位は一長一短。「地元の高校生と共同開発した販売会」の扱いはモデルの方が常識的だが、「定例の社内会議」を最下位にできていない点はベースラインと同じく失敗している。

## 3. 分割 (2 通り、どちらも企業単位)

同じ企業のリリースが train と test に跨ると、モデルは「その企業の平均 PV 水準」を覚えるだけになる。両方の分割で企業を跨らせていない。

| 分割 | 作り方 | train | valid | test | 捨てた行 |
|---|---|---|---|---|---|
| `random` | 企業をシャッフルして 70/10/20 | 89,887 | 13,369 | 25,789 | 0 |
| `temporal` | `created_at` の 80 パーセンタイル (2026-01-29) で切り、後半は**前半に一度も出てこない企業だけ**を test にする | 90,327 | 2,403 | 5,110 | 31,205 |

時系列分割で 31,205 行を捨てているのは、前半に出てきた企業が後半にも出しているリリース。これを test に入れると企業リークになり、train に入れると未来の情報を使うことになるので、どちらにも入れない。結果として test は「カットオフ後に初めて出稿した新規企業」5,110 行 = デプロイ時に実際に起きる状況そのものになる。

valid も同じ手続きを train プールに再帰的にかけているので、早期終了の回数決めにも未来の情報は入っていない。

## 4. 指標

- **Spearman**: test 全行の順位相関。主指標。
- **NDCG@10 (random20)**: test 行をシャッフルして 20 件ずつのグループに刻み、各グループで上位 10 件の NDCG を測って平均。「1 ヶ月ぶんの予定候補から上位を選ぶ」という本番の使い方に対応させたもの。gain は `pv_score` をそのまま使う (0〜1 なので指数 gain にする必要がない)。
- **NDCG@10 (company)**: test に 10 行以上ある企業ごとの NDCG。ランダム分割では 479 社ぶん。**時系列分割では 25 社しか該当せず、この列は当てにならない** (ridge が 0.7211 で首位に見えるのはこのノイズ)。
- **RMSE**: 参考。`lgbm+mlp` だけは順位平均を 0〜1 に均等割り付けした値なので、RMSE は他と比較できない。

| LightGBM + MLP 順位平均 | 0.3564 | 0.7618 | 0.7032 | (比較不可) |

### 5.1 RandomForest はなぜ負けたか

LightGBM と**完全に同じ 259列・同じ企業単位分割・同じ指標**で回しました。結果は上表のとおりで、ランダム分割では k-NN に勝つ (+0.0210、区間も正) ものの LightGBM に -0.042 及ばず、**時系列分割では k-NN ベースラインを -0.0149 下回りました** (区間 [-0.0388, +0.0068] なのでベースラインと有意差なし = 「k-NN を置き換える理由が無い」)。

理由は 2 行で:

1. **RF は独立な木の平均なので、1 本 1 本が単独で目的変数を説明できないと精度が出ません。**256 次元の埋め込みは 1 列あたりの信号が極めて弱く、ランダムに選んだ数十列だけで作った木はほぼノイズになります。GBDT は残差を順に削るので、弱い列の寄与を何百本もかけて積み上げられます。
2. **埋め込みは「多数の弱い列の線形結合」で意味が出る表現で、軸に平行な分割を平均する RF と相性が悪い。**その証拠に、単純な **Ridge (0.4054) が RandomForest (0.3796) を上回っています**。密ベクトルに対しては線形結合の方が素直に効くということです。

補足として RF はカテゴリ 2 本 (業種ID・都道府県ID) を native categorical として扱えず順序値として分割するため、ここでも LightGBM に対して不利です。

**設定と落としたもの** (チューニングはしていませんが、時間とメモリの都合で既定値から 2 箇所落としています):

| 設定 | 値 | 理由 |
|---|---|---|
| `n_estimators` | 200 | 100本で valid Spearman 0.386、200本で 0.396。指定範囲の上限を採用 |
| `max_features` | **0.2** (既定 1.0 から変更) | 既定は毎分割で 259列を全部見るため桁違いに遅い。LightGBM の `feature_fraction=0.2` と条件を揃える意味もある |
| `min_samples_leaf` | **20** (既定 1 から変更) | 葉を 1 件まで伸ばすとモデルが肥大する。20 でも成果物は 77MB (LightGBM の 15 倍) |

### 学習時間 (同一マシン、`meta.json` に記録)

| モデル | ランダム分割 | 時系列分割 | deploy |
|---|---|---|---|
| LightGBM | 23.7 秒 | 16.7 秒 | 18.8 秒 |
| **RandomForest** | **72.1 秒** | **67.8 秒** | **94.4 秒** |
| Ridge | 0.4 秒 | 1.6 秒 | 0.5 秒 |
| MLP | 4.6 秒 | 4.3 秒 | 5.3 秒 |

RandomForest は LightGBM の 3〜5 倍の時間をかけて、精度は下、成果物は 15 倍。採用しない判断に迷いはありません。

### 正直に書くところ

- **時系列分割の勝ち幅は小さい。** Spearman の差 +0.0198 に対して 95% 区間が [-0.0006, +0.0387]。下端がわずかに負に食い込んでおり、5% 水準では「有意に勝った」と言い切れない。test が 5,110 行しかないのが主因で、ランダム分割の 25,789 行では同じ差の推定がはっきり正 ([+0.0537, +0.0727]) になっている。
- **アンサンブルは効かなかった。** LightGBM + MLP の順位平均はランダム分割で +0.0003、時系列分割で -0.0024。単体の LightGBM で十分なので、成果物には入れていない。
- **時系列分割ではベースラインに負けたモデルが 2 つある。**MLP (0.3365) と RandomForest (0.3241) で、どちらも k-NN の 0.3390 を下回った。埋め込みの密ベクトルには MLP や RF が向くかと思ったが、ここでは勾配ブースティングの木だけが安定して勝った。
- どの分割でも Spearman は 0.34〜0.42 の範囲。「読まれやすさ」の 6 割以上は依然として説明できていない。

## 6. 特徴量の取捨

採用したのは **256 次元埋め込み + 業種ID + 都道府県ID + 存在告知フラグ = 259 列**。カテゴリ 2 本は LightGBM の native categorical として渡し、存在告知フラグとの交互作用 (実拠点を持つ業種でだけ効く) は木に判断させている。

開発時の測定 (企業ランダム分割、別 seed、同じ学習設定):

| 特徴 | Spearman | 判断 |
|---|---|---|
| 埋め込み 256 次元のみ | 0.3991 | これだけでベースライン (0.35 前後) を超える |
| + 業種 + 都道府県 + 存在告知 | **0.4039** | **採用** |
| さらに + タイトル長 | 0.4026 | 下がった。事前の「効かない」知見と一致するので入れない |
| さらに + `release_type_id` | 0.4133 | +0.011 効くが**推論時に存在しない**ので入れない (下記) |

`release_type_id` (商品サービス / イベント / 経営情報 ...) は学習データには付いているが、カレンダー上の予定にはまだ付いていない。推論時に渡せない値を学習に入れると train/serve skew になるので、+0.011 を捨てて契約から外した。事前に「効かない」と分かっていた記号・括弧・タイトル長・金額表記・サブタイトル有無、および年号トークンは最初から入れていない。

## 7. 受け入れテスト

6 件の予定文を、業種・都道府県を指定せずに採点した (テキストだけで順位が決まる条件)。ベースラインは全 129,045 件をコーパスとして使い、モデルは `deploy` 版を使っている。

| 予定 | k-NN | 順位 | LightGBM | 順位 |
|---|---|---|---|---|
| 熊本市中央区に新店舗をオープンします | 0.823 | 1 | 0.771 | 1 |
| 創業50周年を迎えます | 0.641 | 2 | 0.607 | 2 |
| 地元の高校生と共同開発したお菓子の販売会 | 0.368 | 5 | 0.504 | **3** |
| 年頭所感を発表します | 0.346 | 6 | 0.492 | 4 |
| 定例の社内会議 | 0.378 | 4 | 0.418 | 5 |
| 新年のご挨拶 | 0.463 | 3 | 0.382 | **6** |

指定された基準「オープン > 年頭所感 > 定例の社内会議」は**両方とも満たしている** (モデルは 0.771 > 0.492 > 0.418)。

- **モデルの方が良い点**: 「地元の高校生と共同開発したお菓子の販売会」を 5 位から 3 位に上げた。地元紙が拾う典型なので、こちらの方が常識に合う。「新年のご挨拶」も 3 位から最下位に落ちており、儀礼的な予定の扱いは改善している。
- **モデルの方が悪い点**: 「定例の社内会議」が 5 位 0.418 で、最下位に落とせていない。**「年頭所感」が 4 位 0.492 と高すぎる**のも問題で、儀礼的な文言 3 件 (年頭所感 / 定例会議 / 新年の挨拶) が 0.38〜0.49 に固まってしまっている。
- **スコアの幅が狭い**: ベースラインの 0.35〜0.82 に対してモデルは 0.38〜0.77。回帰は平均に縮む性質があるので、UI で絶対値を出すなら順位で見せるか、較正 (等順位変換) を挟んだ方がよい。
- 補足: 指示にあったベースライン値 (オープン 0.81 / 年頭所感 0.42 / 定例 0.32) のうち、こちらの再実装では オープン 0.823 は一致したが、年頭所感 0.346 / 定例 0.378 と順位が入れ替わった。業種・都道府県の指定有無かコーパスの版が違う可能性がある。ここは同条件で測り直した方がよい。

## 8. Lambda 見積もり

**推論時に DB もコーパスも参照しない。** 読むのは `artifacts/deploy/lgbm.txt` 1 本だけで、`predict.py` は pandas も scikit-learn も import しない (実際に lightgbm + numpy + scipy だけの venv で動作確認済み)。

### サイズ (x86_64 manylinux、Python 3.13 で実測)

| 中身 | 解凍後 |
|---|---|
| scipy 1.18 (`scipy` + `scipy.libs`) | 110 MB |
| numpy 2.5 (`numpy` + `numpy.libs`) | 56 MB |
| lightgbm 4.7 | 9.3 MB |
| narwhals (lightgbm の依存) | 2.2 MB |
| **依存 合計 (素のまま)** | **178 MB** |
| `tests/` / `__pycache__` / `*.dist-info` / `*.pyi` を削った場合 | **150 MB** (zip 47 MB) |
| モデル `lgbm.txt` (868 本 x 63 葉) | 5.2 MB |
| (参考) `forest.joblib` を載せた場合 | 77.3 MB = **15 倍**。これも RF を選ばない理由の 1 つ |
| **合計 (削った場合)** | **155 MB / 上限 250 MB** |

余裕 95MB。scipy は lightgbm が import 時に必須なので外せない (`lightgbm.compat` が `scipy.sparse` を読む)。それでも収まる。

### レイテンシ (Apple M 系ローカル実測、参考値)

| 項目 | 実測 |
|---|---|
| `import lightgbm` | 942 ms (コールドスタートのみ) |
| モデル読み込み | 45 ms (コールドスタートのみ) |
| 1 件の採点 | 0.09 ms |

コールドスタート約 1 秒、ウォーム時は 1 ヶ月ぶん (30 件) を採点しても 3ms 未満。ボトルネックは OpenAI の埋め込み API 呼び出しの方になる。

### 推論の契約

```python
from ml.predict import PlanScorer

scorer = PlanScorer.load()  # artifacts/deploy/lgbm.txt
scorer.score(vector, "熊本市中央区に新店舗をオープンします", business_category_id=25, prefecture_id=43)  # -> 0.0〜1.0
scorer.score_many(vectors, titles, business_category_id=25, prefecture_id=43)
```

`business_category_id` / `prefecture_id` は `None` 可 (欠損カテゴリ 0 に落ちる。学習データにも県欠損が 15,763 行あるので、モデルはこの値を見たことがある)。

余裕をもう一段増やしたいなら、zip ではなくコンテナイメージ Lambda (10GB) にするか、木を ONNX か純 numpy の走査に置き換えて scipy ごと落とす手がある。今回はどちらも不要と判断した。

```
backend/ml/artifacts/
```

**判断: モデル本体はコミットしない。** `backend/ml/artifacts/.gitignore` を置いて、`plan_vec.npy` と `results.json` だけを残す形にした。

- モデル合計 約 250MB (うち RandomForest 3 分割ぶんで 220MB) は `data/` (既に gitignore 済み) から `train.py` で決定的に作り直せるビルド成果物。git に置く価値がない。
- 一方 `plan_vec.npy` は OpenAI を 1 回叩いた結果で、これが無いと API キー無しでは受け入れテストを再現できない。6KB なのでコミットする。

## 10. 限界と次の一手

- 時系列分割の test が 5,110 行しかなく、勝敗の判定力が弱い。カットオフを 70 パーセンタイルまで下げるか、複数カットオフで rolling 評価すれば差の推定が安定する。
- 儀礼的な予定 (年頭所感 / 定例会議) を下げ切れていない。学習データには「社内会議の告知」がそもそもほぼ存在しないので、モデルは近い事例を持っていない。低 PV 側の事例を意図的に集めるか、ルールで足切りする方が早い。
- 出力が平均に縮んでいる。順位は正しくても絶対値を UI に出すなら等順位変換で較正する。
- `regional_score` は今回予測していない。`app/ranking/score.py` の判断 (地元の話は助言側に回す) に従った。
